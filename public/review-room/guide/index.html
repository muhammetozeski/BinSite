Make revision feedback precise enough to act on

“Move this” is hard to use when there are three image revisions and a long email thread. Client Review Room records which exact file a comment refers to, where the issue appears and which decision follows. Its main workflow uses your local image or video files without an account.

Open Client Review Room

Start with one real delivery

Give the project a useful title and a short delivery brief. Add the actual files you want to review. A logical asset can hold several versions of one image or one video; it is not a folder of unrelated files. Keep a banner and a separate feature card as separate assets.

If you want to inspect the workflow first, open the three editorial example packages. Each package generates two actual PNG files locally and includes clearly labelled example notes. Those are teaching examples, not work performed for a real customer.

What makes one version different from another?

The browser computes a SHA-256 fingerprint from the complete file bytes and records the actual dimensions or video duration. Renaming the same bytes does not create a new revision identity. A changed file should be added as a new version, with a label that helps the next person distinguish it.

Keep your original files. A saved review project contains identities, comments and decisions; it does not embed the media or upload it to an image host. When someone opens your JSON on another device, they reconnect matching originals. A filename alone is not enough to impersonate an existing revision.

Write a comment that points to a decision

For an image, select the exact version and click the relevant place. The marker is stored as coordinates relative to that image. The center action gives a keyboard-accessible way to start a note. For video, pause at the relevant frame and choose Use current video time; the recorded timestamp comes from the real player.

Vague feedbackActionable feedback
“The date is wrong.”“At marker 2 on Version 2, replace the date with the supplied final date before delivery.”
“This part is too fast.”“At the recorded video time, keep the title visible long enough to read it before the next cut.”
“Looks good.”“The currently selected version is ready for review; the remaining open notes are optional refinements.”

Choose a category and distinguish an ordinary note from a blocking change. A blocking change prevents recording approval while it remains open. A note can remain useful without claiming that the whole delivery must stop.

Follow the recorded version, not the newest filename

When an edited file arrives, add it to the same logical asset as a new version. The old comments remain attached to their original bytes. Compare the versions' actual notes and decisions. Resolving an issue on Version 1 does not automatically prove that Version 2 contains the intended correction.

Use comments to explain the expected change. Use the decision controls to record the state of the selected version. Keeping these separate avoids turning a casual note into an accidental approval.

Use the explicit review sequence

  1. Work in Draft while you identify the file and add the initial notes.
  2. Mark the selected version ready for review when that is the actual next step.
  3. Request changes when the file needs another pass.
  4. Resolve every blocking comment before recording approval.
  5. Record delivery only after approval. Reopen review explicitly if another blocking change appears.

This is an editable project record. It is not a signed certificate and does not establish that a named customer personally approved a file. If your business requires a formal signature, keep that separate evidence with your delivery.

Export something the next person can use

The standalone HTML report contains the recorded file identities, comment anchors, decision history and selected version comparison. The open editing list is a CSV of the actual unresolved work. It is more useful than copying a whole conversation into a spreadsheet and losing the connection to a version.

Keep the project JSON as your editable master. Send the original media through a suitable method you control when the recipient needs to inspect it. The report does not silently include those large files.

Optional private collaboration

A real Creator account can save a private metadata workspace and create a viewer or editor invitation. Every invited person can read all shared notes in that workspace. There is no hidden per-comment privacy field. Recipients still reconnect matching original media locally.

A workspace label is a short cloud-list label; the complete project title stays inside the document. A save includes the revision that you actually loaded. If another editor saved first, preserve your local JSON and deliberately reload or make a separate copy instead of overwriting their changes.
