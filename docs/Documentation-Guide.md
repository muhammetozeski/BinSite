# Writing and maintaining project knowledge

Read the index before researching a topic. Update the existing source of truth when its behavior changes; avoid parallel descriptions. Use English for project documentation and complete Turkish for product copy.

Document learned implementation contracts, relationships, verified deployment methods, and diagnosed failures. State whether the support is source inspection, official provider documentation, a local check, or a production observation. Do not turn an unexecuted proposal into a working method. Include the conditions that affect the conclusion and the real file/function or source URL supporting it.

Create subject-based articles only when there is useful knowledge to preserve. Add a short index link explaining when to read each article. A method needs its prerequisites, action, expected result and verification; a diagnosis needs its distinguishing symptom, demonstrated cause and tested remedy. Do not copy raw logs, broad file inventories, secrets, routine task diaries or speculative roadmaps into articles.

Keep transient reports and business proposals outside the knowledge library. After a meaningful result, append a concise dated Walkthrough record that links to the relevant article instead of repeating it. Preserve user instructions at their actual scope; never record assumed approval. Check only links and claims affected by the current edit, using existing evidence whenever it remains applicable.
